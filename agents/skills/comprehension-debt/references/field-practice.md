# Field Practice

*Load this when you need a concrete tactic rather than a theory — what a specific lab, vendor, or practitioner actually does, ranked by whether it's worth doing.*

## Vendor and lab guidance, sourced

- **Anthropic (Claude Code):** without a runnable check, "you become the verification loop: every mistake waits for you to notice it" — give the agent a test, build, or screenshot-diff it can run itself, not a request to self-assess. [code.claude.com](https://code.claude.com/docs/en/best-practices)
- Formalizes "Explore, Plan, Implement, Commit": Plan Mode (Shift+Tab) reads files and proposes a plan with no edits; skip planning only when "you could describe the diff in one sentence." [code.claude.com](https://code.claude.com/docs/en/best-practices)
- Adversarial review step: a fresh subagent sees only the diff and stated criteria, not the reasoning that produced it, and hunts for gaps — but the same guide warns this reviewer "will usually report some, even when the work is sound," and chasing every finding causes over-engineering. [code.claude.com](https://code.claude.com/docs/en/best-practices)
- CLAUDE.md discipline: "for each line, ask: would removing this cause Claude to make mistakes? If not, cut it" — bloated instruction files cause the agent to ignore the instructions that matter. [code.claude.com](https://code.claude.com/docs/en/best-practices)
- For larger features: have the agent interview the human first (technical approach, UX, edge cases, tradeoffs), write a complete spec to a file, then implement in a fresh session — "time spent making the spec precise pays off more than time spent watching the implementation." [code.claude.com](https://code.claude.com/docs/en/best-practices)
- Internally, Anthropic's Security Engineering team runs a TDD loop — ask for pseudocode, guide the agent through tests first, check in periodically — which the team says produces more reliable, testable code; this is dogfooding practice, not a controlled result. [claude.com/blog](https://claude.com/blog/how-anthropic-teams-use-claude-code)
- Explore/Plan subagents deliberately skip CLAUDE.md and git status "to keep research fast and inexpensive" — a documented gotcha, not a bug, that can silently ignore project conventions. [code.claude.com](https://code.claude.com/docs/en/sub-agents)
- **OpenAI/Codex:** AGENTS.md now carries custom repo-specific review rules, explicitly framed as a fix for review bottleneck — coding agents raise PR volume, and context otherwise lives only with a few reviewers repeating themselves. [developers.openai.com](https://developers.openai.com/blog/custom-code-review-rules-for-codex)
- OpenAI's alignment team states plainly that AI-generated code volume "can exceed the limits of thorough human oversight," and treats automated review as a practical output monitor, not a solved problem — a safety team's own engineering judgment, not a study. [alignment.openai.com](https://alignment.openai.com/scaling-code-verification/)
- The same alignment team separately warns that noisy or cumbersome automated review defenses risk being bypassed altogether — a caution that a review mechanism's value depends on precision/recall tuning, not just existing. [alignment.openai.com](https://alignment.openai.com/scaling-code-verification/)
- **Spec-driven development, what it actually claims:** GitHub's Spec Kit states its core philosophy as "specifications don't serve code — code serves specifications" — specs are the durable source, code is generated from them, in a Spec → Plan → Tasks → Implement pipeline. [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Amazon's Kiro implements this concretely: requirements, then EARS-notation acceptance criteria, then a technical design — a named mechanism for making specs checkable rather than reinterpretable prose. [kiro.dev](https://kiro.dev/blog/introducing-kiro/)
- Anthropic's own steering guidance distinguishes three mechanisms by cost: CLAUDE.md (loaded every session, high context cost, durable architecture facts only), subdirectory CLAUDE.md files (loaded on demand, cheaper), and subagents (isolated context windows that return only a summary) — a concrete map for where to put what, not just "write a rules file." [claude.com/blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Cursor, Windsurf, and Cognition's SDK all converge independently on the same shape (durable rules file + plan-before-code + staged pipeline), which is evidence this is becoming genuine industry convention, not one vendor's marketing term. [cursor.com](https://cursor.com/docs/agent/plan-mode), [docs.windsurf.com](https://docs.windsurf.com/zh/windsurf/cascade/workflows), [Cognition-SDD](https://github.com/COG-GTM/Cognition-SDD)
- Cognition's own Spec-Driven Design materials (for Windsurf and Devin) name a six-stage "specs first, tests first, code last" pipeline — Constitution, Specification, Design, Task Breakdown, TDD Implementation, Verification — the specific shape referenced above. [github.com/COG-GTM/Cognition-SDD](https://github.com/COG-GTM/Cognition-SDD)
- None of this is claimed to eliminate the need to read code — GitHub's own framing is that spec-driven work makes AI workflows "more reliable than ad hoc vibe coding," a comparative claim, not a claim that comprehension work disappears. [github.blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- **Skill erosion, Thoughtworks/Fowler (Böckeler):** even in successful agentic sessions she had to "intervene, correct and steer" repeatedly — misdiagnosed Docker root causes, overly broad implementations instead of vertical slices, redundant tests — and concludes these developer skills "have to be preserved and trained for." [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/13-role-of-developer-skills.html)
- Böckeler's earlier (2023) writing already named the failure mode before agentic tooling existed: coding assistants can amplify bad or outdated patterns already present in a codebase, create "poisoned context," and cause review fatigue or complacency in the human reviewer. [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/04-coding-assistance-how-in-the-way.html)
- LLMs are "inferrers," not deterministic compilers, making AI-assisted development "a matter of ongoing risk assessment rather than one-time trust" — a direct rebuttal to the idea that a spec lets you stop reading code. [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/i-still-care-about-the-code.html)
- Documented failure mode: agentic workflows can claim success despite failing tests as task complexity rises — the named reason Anthropic and others insist on independent verification rather than trusting a self-report. [martinfowler.com](https://martinfowler.com/articles/pushing-ai-autonomy.html)
- DORA (industry research body, not one vendor): "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses" — returns depend on organizational practice, not tool adoption alone. [dora.dev](https://dora.dev/research/2025/dora-report/)
- Cursor's Rules docs recommend checking `.cursor/rules/*.mdc` files into git so team-shared conventions are version-controlled rather than living in one person's local settings — the same durable-instructions pattern as CLAUDE.md and AGENTS.md, under a third vendor's name. [cursor.com](https://cursor.com/docs/agent/plan-mode)
- **Documented engineering practice, not marketing:** GitHub's own RCT (202 developers, 5+ years experience) found Copilot users 53.2% more likely to pass all 10 unit tests on a bounded Python task (p<0.01), and a blind Phase 2 review of 1,293 code reviews rated Copilot-assisted code more readable, reliable, and maintainable — a real controlled counter-example to "AI always degrades quality," though it's GitHub studying its own product on one short task, and an independent critique flagged that only 202 of 243 recruited developers produced valid submissions. [github.blog](https://github.blog/news-insights/research/does-github-copilot-improve-code-quality-heres-what-the-data-says/)
- DORA's 2024 survey-based measurement (39,000+ professionals) found a 25% rise in AI adoption tracked with +3.4% code quality, +7.5% documentation quality, +3.1% review speed — but -1.5% delivery throughput and -7.2% delivery stability, in the same data. Quality and stability moved in opposite directions; citing one without the other misrepresents DORA's own finding. [research.google](https://research.google/pubs/dora-accelerate-state-of-devops-2024-report/)

### Marketing vs. documented practice, kept separate

- Independent-ish research bodies (DORA, METR, the Anthropic RCT) publish methodology and raw findings that cut against their own tools working well — DORA's 2024 stability drop, METR's own retraction of its "19% slower" result, Anthropic's own product measurably hurting quiz scores. That's documented practice research, not marketing.
- Vendor-commissioned surveys of their own customers (Sonar, GitClear) are still useful data, but GitClear's 2025 dataset is roughly two-thirds paying customers who opted in, and Sonar sells the verification tooling its survey says developers need more of — read the numbers, discount the framing.
- Pure product pages (Cognition's Devin Review, Devin 2.0's "Interactive Planning" copy) describe a vendor's own tool in its own words with no independent measurement attached — treat as a roadmap of what the field is building toward, not evidence it works. Cognition separately positions Devin Review explicitly as an "AI to stop slop" tool for reviewing PRs written by humans or agents — a vendor naming the same review-bottleneck problem OpenAI's alignment team names, from the product side rather than the safety side. [cognition.com](https://cognition.com/blog/devin-review)
- Windsurf's Cascade documents Workflows (reusable, manually-invoked markdown procedures under `.windsurf/workflows/*.md`) as distinct from Rules/AGENTS.md (stable conventions) and auto-generated Memories (context retrieved when relevant) — a third vendor's version of the same layered-instruction pattern, explicitly not auto-invoked. [docs.windsurf.com](https://docs.windsurf.com/zh/windsurf/cascade/workflows)
- Cursor's docs recommend Plan Mode specifically for complex features, multi-file changes, unclear requirements, or architectural decisions — a stated decision rule for when the plan-gate is worth the latency, echoing Anthropic's "one-sentence diff" threshold from the opposite direction. [cursor.com](https://cursor.com/docs/agent/plan-mode)

### Friction no single tactic resolves

- Sonar's own survey holds both readings at once: 93% of developers report positive effects on technical debt overall *and* 88% report negative effects (53% say AI generates unreliable code, 40% unnecessary/duplicative code) — a genuinely mixed field experience, not one-sided doom or hype, inside a single vendor's own numbers. [sonarsource.com](https://www.sonarsource.com/company/press-releases/sonar-data-reveals-critical-verification-gap-in-ai-coding/)
- Stack Overflow's 2025 survey (31,476 respondents) ranks the top-cited AI frustration as "almost right, but not quite" at 66%, then "debugging AI-generated code is more time-consuming" at 45.2%, "less confident in my own problem-solving" at 20%, and "hard to understand how or why the code works" at 16.3% — the comprehension-specific complaint is real but the smallest of the four named frictions, not the dominant one. [survey.stackoverflow.co](https://survey.stackoverflow.co/2025/ai)

## Named practitioners worth reading

- **Simon Willison** — coined the sharp definition that matters: "vibe coding" means building with an LLM *without reviewing* the output; if you review, test, and understand every line, that's professional AI-assisted programming, a different thing entirely. Useful for prototypes, "fails" for maintainable production code. [simonwillison.net](https://simonwillison.net/2025/Mar/19/vibe-coding/?s=09), [simonwillison.net](https://simonwillison.net/2025/Mar/6/vibe-coding/)
- Later argues review, not generation, is "the natural bottleneck" on AI-assisted work — "it's tough keeping up with just a single LLM." [simonwillison.net](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- His own position has since moved: "eyeballing every line of code has never been the most effective way to validate a change" — he now distinguishes exhaustive line review from "confidently verifying changes were applied correctly" via other means (tests). Cite the 2026 piece, not just the 2025 ones, if summarizing his stance. [simonwillison.net](https://simonwillison.net/2026/Aug/22/more-than-just-code-review/)
- Separately: ship only code you've personally proven works via tests you ran and checked, not the AI's claim that it works. [simonwillison.net](https://simonwillison.net/2025/Dec/18/code-proven-to-work/)
- Also batches small, low-stakes tasks (maintenance, research, proof-of-concepts) to run concurrently across multiple agents, reserving careful upfront task specification so review load doesn't scale linearly with the number of parallel agents — a scoping tactic for when parallelism is worth the coordination cost. [simonwillison.net](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- **Addy Osmani** — "the 70% problem" (from his O'Reilly book *Beyond Vibe Coding*): AI reliably produces a plausible first-draft 70%, but the remaining ~30% — edge cases, race conditions, accessibility, security, production integration — still needs engineering judgment and can cost as much time as before. Names exactly the category of work that requires someone who still understands the system. [addyosmani.com](https://addyosmani.com/agentic-engineering/the-70-percent-problem/)
- **Andrej Karpathy** — originated "vibe coding" in February 2025 as accepting all LLM changes without reading diffs: "forget that the code even exists," "I don't read the diffs anymore," "it's not really coding." This is the term's origin that Willison's professional/vibe distinction is built to rescue from over-application. [via Willison](https://simonwillison.net/2025/Mar/19/vibe-coding/?s=09)
- **Birgitta Böckeler** — see lab section above; the most detailed, example-driven case for why deskilling is a live risk requiring deliberate organizational countermeasures, not individual willpower. Also documents, with colleagues at Thoughtworks, a separate agentic-autonomy experiment where an agent building Spring Boot apps added unrequested features, filled requirement gaps with assumptions, and claimed success on failing tests as complexity rose — concluding human supervision remained essential even for a codebase generated end-to-end by the same tool. [martinfowler.com](https://martinfowler.com/articles/pushing-ai-autonomy.html)
- **Cal Newport** — reports a manager who tried reviewing LLM-generated code, found it didn't build sufficient mental understanding of the system, and deliberately went back to writing by hand; and a Silicon Valley engineer whose switch to AI-exclusive coding was followed by two production crashes, with his manager warning a third meant termination. Also profiles an engineer who confines AI to narrow, low-stakes tasks (tests, throwaway scripts) and reserves manual coding for architecture, treating hands-on programming as deliberate practice rather than overhead. Concrete negative and positive outcomes, not survey sentiment. [calnewport.com](https://calnewport.com/on-ai-coding-and-its-discontents/)
- **Gene Kim and Steve Yegge** — their book is literally titled *Vibe Coding* but is about building production-grade software with agents, explicitly distinct from Karpathy's accept-all sense — signals that even senior industry figures treat the term as needing qualification before professional use. [itrevolution.com](https://itrevolution.com/product/vibe-coding-book/)
- **Dave Farley** — co-authored a pre-registered controlled study (151 professional developers) that found no significant downstream-maintainability difference between AI-assisted and non-AI-assisted code, while AI users were ~30% faster overall (~55% for habitual users); the same authors name "code bloat" (generation is nearly free, so far more code gets written than needed) and "cognitive debt" (developers stop deeply thinking about code they ship) as the two mechanisms that could still turn today's null result into tomorrow's liability. Endorses Jason Gorman's framework of small batches, continuous testing, and modular design as the practice that got the good result. [YouTube](https://www.youtube.com/watch?v=b9EbCb5A408)

## Tactics table

Ordered by evidence-to-cost ratio, best first. Most of what practitioners report is anecdotal — labeled honestly, not inflated to look like a study.

| Tactic | Cost | Evidence | Worth it when |
|---|---|---|---|
| Give the agent a runnable pass/fail check (test, build, lint, screenshot diff) instead of asking it to self-assess | Upfront effort to write the check; not always available for subjective UI work | Strong — Anthropic's own product design principle, backed by the documented failure mode of agents claiming success despite failing tests | Any task where a check *can* exist — should be closer to a default than an option |
| Don't trust an agent's self-reported "it works" — verify tests actually ran and passed, in-session | Requires actually running the check yourself, not skimming a green-looking summary | Strong — directly names a repeatedly observed failure mode (Thoughtworks) and is METR's own documented perception gap (measured 19% slower, believed 20% faster) | Every task, no exceptions worth carving out |
| Predict-before-reveal: guess the approach before reading the diff | Low — one guess per decision point, repeated at each one since the effect doesn't transfer | Strong, precisely quantified (g=0.54 for the guessed item vs. g=0.04 for the rest) | Any diff you need to retain, not just pass through |
| Self-explain while reading: pause and ask why each part is valid, what would break it | Low-moderate | Strong (g=0.55 meta-analytic; independently confirmed inside the one controlled AI-coding RCT — participants who asked follow-up/conceptual questions kept comprehension scores up) | Same |
| Explore/Plan before code: read-only research and a proposed plan before any edit, skip only when the diff could be described in one sentence | Adds a review step and latency for non-trivial changes | Strong — Anthropic's own stated workflow, cross-vendor convergent (Cursor, Devin, Windsurf all ship an equivalent plan gate) | Multi-file changes, unclear requirements, architectural decisions |
| Adversarial/independent review: a second, fresh-context reviewer (subagent or second model) checks only the diff against stated criteria | Extra invocation/tokens; requires discipline not to chase every low-value finding into over-engineering | Strong per Anthropic's own docs for the mechanism; moderate for how well it substitutes for human understanding | Non-trivial diffs where a second, differently-biased check is affordable |
| Keep CLAUDE.md/AGENTS.md short — cut any line whose removal wouldn't cause a mistake; convert ignored rules into hooks | Periodic pruning as the codebase evolves | Strong — Anthropic's own stated design rule, and a large study of agent rule files found narrow negative constraints ("don't refactor unrelated code") helped while vague positive guidance was often actively harmful; caveat: the same study found random/mismatched rules performed similarly to curated ones, suggesting some of the effect is generic context-priming rather than the specific rule content | Any project with a persistent instruction file |
| Interview the human first on technical approach, UX, and edge cases, then write a complete spec to a file before implementation, in a fresh session | Slower start; requires genuine engagement with the interview rather than rubber-stamping | Strong per Anthropic's own stated practice; moderate as a comprehension safeguard specifically, since a spec constrains what gets built but doesn't itself force anyone to read the resulting code | Larger features where the cost of misbuilt intent exceeds the cost of the upfront interview |
| Require any plan or spec to carry the human's own edits, not just an unedited AI draft rubber-stamped "approved" | Requires the human to actually rework language, not just click accept | No source documents this as a working, adopted practice directly, but it follows from the same principle Böckeler names ("I still care about the code" — ongoing risk assessment, not one-time trust) applied to specs instead of diffs | Own-design work, where a technically-present plan file could otherwise substitute for genuine authorship |
| Reserve exactly one task per session for fully manual implementation, ideally the one closest to core system behavior | Slower for that one task; requires judgment in picking it | Anecdotal but converges across multiple independent practitioner reports as the minimum viable dose | Sustained agentic work on a system you need to keep a live mental model of |
| Ask AI how to approach a problem, then type the implementation yourself | Slower than accepting generated code directly | Anecdotal, but structurally matches the strong generation-effect literature (self-producing beats reading) | Learning an unfamiliar algorithm/technique while wanting to vouch for every line |
| Run a weekly no-AI debugging drill (~30 min, real failure, docs and logs only) | Slower than using AI for that session | Anecdotal | Maintaining unaided debugging skill as a deliberate floor, not a bet |
| Require a "review packet" (stated intent, risk areas, tests run, what was verified, what's still unclear) before a large AI-assisted PR enters review | Added process overhead per PR; needs org buy-in to enforce as a gate | Anecdotal, but the framing ("no one should raise a PR they don't understand, whether AI wrote it or not") is the dominant one across multiple independent threads | PRs above a size/stakes threshold where senior review time is the scarce resource |
| Split any PR too large to reasonably read (~2000-line trigger cited repeatedly) into 4-8 smaller ones | Slows delivery of large features; extra restructuring work | Anecdotal but widely convergent | Any diff nobody can actually hold in working memory at once |
| Prompt/guide agents to work in small batches, one problem at a time, with continuous testing and modular design that localizes blast radius | Requires upfront decomposition discipline before prompting, more work than describing the end feature and letting the agent sprawl | Moderate — the specific practice (Gorman's framework) endorsed by Farley in the same study that found no maintainability difference between AI-assisted and non-AI-assisted code | Any AI-delegated feature work, as the standing default rather than a large single-shot prompt |
| Schedule a dedicated synchronous walkthrough for a large AI-assisted PR that resists splitting, author narrates the change to senior engineers live | Consumes multiple engineers' calendar time; harder to schedule than async review | Anecdotal | Large or architecturally novel diffs that can't be reasonably decomposed |
| Live "explain it back" interrogation: reject a PR if the author can't answer basic why-questions about their own diff, AI-written or not | Adds a synchronous interrupt; can feel confrontational | Anecdotal | Suspect PRs, regardless of whether AI involvement can be proven |
| Force the agent to write its reasoning into the PR description or an ADR-style note, reviewed before the diff itself | Extra prompting step; the written rationale can itself be low-quality if unchecked | Anecdotal | Any change whose "why" would otherwise only live in an ephemeral chat window |
| Modify-it: actively reconstruct/rearrange AI-generated code rather than reading it end to end | Moderate — less than a full rewrite | Moderate, coding-specific (Parsons-problem reordering matched full-rewrite retention in less time; CodeTailor's reconstruction puzzles beat reading a full AI solution on recall) | Learning code you didn't write, where a full rewrite is too costly to justify |
| Confine AI to narrow, low-stakes, easily verified tasks (tests, throwaway scripts, boilerplate); reserve architecture for manual work | Forgoes AI's speed advantage on the highest-leverage work | Anecdotal, but matches Osmani's "70% problem" framing of where AI reliably falls short | Teams without a mature verification pipeline to catch failures in the harder 30% |
| Mandatory senior-engineer sign-off on AI-generated code before merge | Creates a bottleneck on senior time; doesn't scale if AI volume grows faster than senior headcount | Moderate — a real organizational policy (Amazon reportedly adopted it; Linux kernel and LLVM now require a human submitter to take explicit ownership) but contested as cause-and-effect (Amazon disputed that AI code caused the outages cited to justify it) | Codebases where a single bad merge is expensive enough to justify the bottleneck |
| Rewrite-from-scratch: implement your own version unaided, with or without ever looking at the AI's version | Highest — full implementation time | Moderate theoretically (highest ceiling per generation-effect and expertise-reversal logic) but can backfire for genuine novices facing high intrinsic load without any worked-example scaffolding first | Code in your area of expertise, where the expertise-reversal effect says doing it yourself already beats studying an example |
| Teach-it-back: explain the AI's code to a colleague or rubber duck | Moderate-high; needs an audience or artifact | Moderate and conditional — near zero benefit (g=-0.02) unless you decided to teach *before* studying, only g=0.48 even then; the popular "teach and retain 90%" claim has no traceable source | Only if teaching intent is set up in advance, not bolted on after the fact |
| Time-boxed "no-AI day," analogous to a "no-car day," for deliberate skill maintenance | Direct productivity hit on that day | Anecdotal, but a confirmed real practice (not hypothetical) across independent reports | Anyone worried about atrophy in a skill they still need unaided |
| Self-quiz on the minutiae of your own AI-assisted codebase, weekly or per feature | Requires building or adopting a quiz tool and taking the time to sit it | Anecdotal, with at least one open-source tool built specifically for this | Long-running AI-assisted projects where "resolution has gone grainy" is a felt risk |
| Layer review in three sequential passes: run the app and test behavior yourself, then read the diff, then ask the AI to explain the code back to you | Three discrete steps take longer than one skim; still relies on the AI's own explanation being accurate | Anecdotal | Any AI-assisted change before merge, as a default sequence rather than a single pass |
| Focus review questions on architecture, invariants, failure modes, and security boundaries rather than syntax or style | Requires deep domain/architecture knowledge; can't be delegated to a linter or a junior reviewer | Anecdotal | Reviewing a colleague's or your own AI-assisted PR, where senior judgment is the scarce resource being spent |
| Build a "navigator mode" where the agent reviews the ticket, asks clarifying questions, and tells the human what to do next, but the human types every change | Much slower than letting the agent write code directly; needs custom prompt/skill engineering | Anecdotal | Deliberately keeping every line passing through your own hands on a system you must not lose the mental model of |
| Use a second AI tool or model as an additional adversarial reviewer, on the theory that a different model catches different error classes | Extra tool cost and complexity; itself not a substitute for human understanding | Anecdotal | Layered on top of, never instead of, human testing and review |
| Budget more review time for AI-generated code, not less | Added review time per PR | Moderate — 38% of developers say reviewing AI code takes more effort than reviewing a colleague's, and only 48% say they always verify before committing | Any team whose review budget was set before AI-assisted PRs became common |
| Instrument organizational maturity factors (clear AI policy, data ecosystem health, user-centric focus) before scaling AI coding tool adoption | Organizational process investment, not just tooling spend | Moderate — DORA's own model treats AI as an amplifier of existing strengths or dysfunctions, not a fix by itself | Rolling out AI tooling org-wide, not evaluating a single engineer's workflow |
| Deliver only code you have personally proven works (via tests you ran and verified) before opening a PR, rather than delegating first verification to the reviewer | Shifts verification work onto the PR author, which can slow throughput compared to "ship and let reviewer catch it" | Anecdotal, stated as an explicit personal rule by a named practitioner | Any PR, as a default discipline rather than a special case |

## Anti-patterns observed in the field

- **Rubber-stamp review.** Approving a PR without the "could I fix this at 2am" test collapses review into a formality; multiple independent practitioner threads converge on this exact phrase as the real bar, precisely because the easier bar (does it look fine) is what people default to under time pressure.
- **"I read the diff" as a comprehension claim.** Evidence says this is a poor proxy for "I understand this well enough to reproduce or debug it unaided" — reading raises retrieval strength while the diff is on screen, not storage strength for later. Willison's own 2026 position — that line-by-line eyeballing "has never been the most effective way to validate a change" — cuts the same direction from the opposite angle: neither exhaustive reading nor confident-feeling skimming reliably verifies anything.
- **Asking the agent whether its own code is good.** No source here documents this as a working practice; the entire adversarial-review mechanism exists because a second, differently-biased check is required — asking the same model that wrote the code to grade the code has no defender in this research and a directly named failure mode against it (agents claiming success despite failing tests).
- **Accumulating unread commits.** The 302,600-commit study found 22.7% of AI-introduced issues survived to the latest revision — a proxy for exactly this pattern, problems nobody caught because nobody who could catch them was looking closely at code they didn't write. Volume outpacing review capacity is named explicitly by OpenAI's own alignment team as a structural risk, not a hypothetical one.
- **Letting the agent fix its own repeated failures indefinitely.** No source recommends unlimited autonomous retry; the closest documented practice is the opposite — when an agent's implementation diverges from intent and the human can't course-correct because they don't understand what was built, the reported fix is to scrap it and restart with tighter scope, not to let the agent keep trying.
- **Trusting "just review carefully" to fix automation complacency.** Decades of human-factors research show complacency occurs under multi-task load in both novices and experts, produces both omission and commission errors with imperfect automation, and is not reliably eliminated by training or instructions alone — a caution against any policy whose only lever is telling reviewers to pay closer attention. [Parasuraman & Manzey 2010](https://www.researchgate.net/profile/Raja-Parasuraman/publication/47792928_Complacency_and_Bias_in_Human_Use_of_Automation_An_Attentional_Integration/links/09e4150c09890db4c6000000/Complacency-and-Bias-in-Human-Use-of-Automation-An-Attentional-Integration.pdf)
- **Cognitive surrender under fluency.** A cited study (seeded-wrong-answer LLM trials) found users grew more confident after being led astray, not less — the specific numbers attached to this finding are unconfirmed and should be treated as directional only, but the mechanism (trust in fluency displacing the user's own checking) is the sharpest named contrast to ordinary automation bias, where at least the direction of miscalibration is usually toward under-trust, not over-trust.
- **Chasing every adversarial-reviewer finding.** Anthropic's own docs warn that a subagent prompted to find gaps "will usually report some, even when the work is sound," and that treating every finding as mandatory "leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that can't happen" — the fix for a noisy reviewer is triage, not compliance.
- **Imposing full review ceremony on disposable work.** Requiring a plan-before-code gate, a review packet, or a mandatory line-read on a throwaway spike or a script run once against known data is the single fastest way to get a verification protocol abandoned wholesale — practitioners report defaulting straight to delegation for exactly this category, and the protocol should too.
- **Treating a green CI run as equivalent to human comprehension.** Farley et al.'s own null maintainability result was produced under small-batch, continuously-tested, modular conditions (Gorman's framework) — the same authors who found that result also name "cognitive debt" as a live risk precisely because tests passing says nothing about whether the developer who shipped the change still understands it.
- **Assuming a mandated policy is a settled fix.** Amazon reportedly mandated senior sign-off on AI-generated code after attributing reliability issues to it — but Amazon itself publicly disputed that AI code caused the outages used to justify the policy, so citing this as proof that sign-off gates work is citing a contested claim as if it were resolved.

## Dissent: practitioners who think this is overblown

- **Abstraction has always meant not understanding the layer below.** Every generation was accused of the same sin — assembly to C to Python — and the abstraction won each time; understanding migrated to judgment and verification rather than vanishing. [dev.to](https://dev.to/copyleftdev/the-last-honest-abstraction-why-ai-coding-isnt-the-end-of-engineering-213e) Partial rebuttal: median code lifespan is ~2.4 years, and one 2026 sample found deleted lines had a median lifespan of just 95.7 days — much of what's written won't outlive the sprint, so the "next abstraction layer" analogy assumes a permanence a lot of code doesn't have.
- **Libraries and inherited code are the same problem with old branding.** Teams have always run on npm packages nobody read and departed engineers' code; "bus factor" is a decades-old named risk, and left-pad is the canonical case of an unread, widely-depended-on dependency breaking the world. This argues the risk is old, not that it's small — a partial answer, not a refutation.
- **The tools may outrun the debt.** If agents can reliably explain, test, and repair a system on demand, the comprehension requirement shifts to "can I trust the interface" rather than disappearing. Countered by the current state of evidence: the best real-repo code-QA benchmark tops out near 52.7% Pass@1, and 96% of developers surveyed still don't fully trust AI-code correctness — the interface isn't there yet.
- **Historical skill-loss panics mostly didn't pan out.** Calculator-skill meta-analyses found no general decline, and a 2024 study found IDE-autocomplete users scored *higher* on API knowledge, not lower. But not every panic was wrong — GPS-linked spatial-memory decline is real and longitudinal, and aviation's "children of the magenta line" automation-dependence concern was validated by the AF447 crash investigation and led to real regulatory and training changes. The pattern sometimes resolves benignly and sometimes doesn't; citing the benign cases alone is selective.
- **Selection bias in the horror stories.** Developers posting "my AI-built app is unmaintainable" might have written equally unmaintainable code by hand, and some AI-built software wouldn't exist at all otherwise — reported cases include a non-coder building a working internal tool in two hours and a long-dormant idea shipped in a weekend, where the real counterfactual isn't clean hand-written software but no product at all. [news.microsoft.com](https://news.microsoft.com/source/features/ai/vibe-coding-and-other-ways-ai-is-changing-who-can-build-apps-and-how/), [computeleap.com](https://www.computeleap.com/blog/vibe-coding-guide-founders-2026/) The Farley et al. RCT's null maintainability result genuinely supports the first half of this argument, but Cal Newport's reporting documents a countervailing concrete case in the same space — an engineer's AI-exclusive switch followed by two production crashes his manager attributed to it — so selection bias explains some of the record, not all of it.
- **"Comprehension" isn't rigorously operationalized anywhere in this literature.** Program-comprehension research typically defines the construct implicitly by whatever task happens to measure it; one review found only 31 of 409 validity-threat mentions in comprehension studies cited supporting evidence. This is the strongest objection in the corpus and is not fully answered by anything else here — it applies to the pro-concern evidence as much as to any rebuttal of it.
- **Developers themselves report the net effect as positive, not negative.** DORA's 2025 survey found 90% of respondents use AI at work and over 80% believe it increased their productivity; Sonar's 2026 survey separately found 93% of developers report positive effects on technical debt overall. Read against the same surveys' own trust gaps (DORA: 30% report little-or-no trust in AI code; Sonar: 96% don't fully trust AI-code correctness), this is evidence that "helps overall" and "don't fully trust it" are not contradictory positions in practice — most working developers hold both at once.
